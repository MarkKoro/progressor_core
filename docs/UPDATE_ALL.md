# Обновление всех четырёх продуктов

После подключения к серверу достаточно одной команды:

```sh
update-all
```

Gym, Food, Supply и Progressor Core получают актуальную `main` из своих репозиториев
MarkKoro. Команда сначала готовит код и недостающие зависимости, запускает тесты с
временными базами и тестовыми ключами, проверяет общие адаптеры и создаёт резервную
копию всех четырёх приложений. Копии SQLite отдельно восстановлены и проверены.
Работающие процессы продолжают работать во время подготовки.

Переключаются только изменённые продукты; Core перезапускается после изменения
источников. Учитываются оба действующих Food API и отдельный Supply worker. Текущее
задание worker должно закончиться до переключения. Новое Python окружение создаётся
отдельно, когда установленные пакеты не соответствуют требованиям. Прежние пакеты
не меняются. При неизменных версиях и подходящих пакетах перезапусков нет.

Проверяются все службы, HTTP, стабильность процессов, единственный Telegram consumer
каждого бота и свежая синхронизация всех трёх источников. Итог содержит четыре строки
`Gym/Food/Supply/Core: OK`, версии Git и путь журнала.

Ошибка после начала переключения возвращает **все затронутые** версии кода, Git refs,
окружения и настройки запуска. SQLite остаются действующими: новые записи людей,
платежи и возвраты не заменяются старой копией. Если команду прервали, следующий
`update-all` сначала завершит восстановление, затем заново подготовит обновление.
Блокировка запрещает одновременные обновления.

После активации owner-consent-v1-ready откат также обязан сохранять новую границу
чтения Supply. Несовместимые старые reader/updater команда не восстанавливает:
она сохраняет совместимый текущий выпуск и сообщает, что восстановление требует
внимания. Это отказ от небезопасного отката, а не успешное обновление.

```sh
update-all --check
```

Это проверка GitHub, требований и текущего запуска без установки и переключения.
`updateall` — короткое альтернативное имя. `update_food`, `update_supply`,
`update_gymdiary`, `update-progressor` и `updatecore` используют тот же механизм для
одного продукта. Общие адаптеры обязаны оставаться совместимыми со всеми остальными;
для согласованного изменения используйте `update-all`.

Старая `update_all_bots` относится к FaceBot/Toro/ReShala и сохранена отдельно.

Единственный источник команды — `deploy/update_all.py` в этом репозитории.
`/srv/progressor_core/updater/` содержит проверенную установленную копию для запуска;
она обновляется только после успешного выпуска Core. Это позволяет запустить откат,
даже если новое приложение не стартовало. Сам Core тоже существует только здесь;
не копируйте его в репозитории ботов.

Закрытый журнал: `/root/progressor-deployments/update-all/<UTC-pid>/`.
Состояние восстановления: `/srv/progressor_core/updater/update-all-state.json`.
Резервные копии: `/root/progressor-backups/*-all-update.tar.gz`; команда выводит SHA256.
В архив кода и настроек отдельно входят существующие постоянные маркеры
`/var/lib/progressor/bundle-v2-ready` и `owner-consent-v1-ready`: наличие каждого,
размер, SHA256 и режим файла записаны в manifest. Архив проверяется на точные байты
и режим. Недоступный, не обычный, слишком большой или небезопасно доступный для
записи маркер останавливает создание копии; отсутствие до активации записывается
явно. Изменение наличия или содержимого во время копирования тоже останавливает
его. Обычный откат кода не восстанавливает и не удаляет эти постоянные маркеры.
Старые выпуски и окружения сохраняются. Команда держит запас свободного места:
не меньше 2 ГБ или 10% диска плюс оценка размера ближайшей операции. При нехватке
места обновление прекращается до переключения. После успешного обновления сохраняются
последние три проверенные копии именно `*-all-update`; более старые копии этой команды
удаляются после сверки SHA256/manifest. Незнакомые, неполные и чужие архивы не удаляются.
Это копии приложений, а не полный образ VPS;
для защиты от потери сервера скачивайте архив на другое устройство. Ключи и данные
из архивов нельзя публиковать в GitHub.

Приватные `.env`/ключи/живые базы не подтягиваются из Git. Новые обычные Python пакеты
устанавливаются автоматически. Если изменению нужен новый секрет, системный пакет
или несовместимая миграция базы, подготовьте это отдельно по инструкции изменения.
Команда остановит неудачный выпуск; обратную миграцию пользовательских данных она
не выполняет. Миграции приложений должны сохранять совместимость предыдущего кода.


Финансовая версия2: после включения bundle-v2-ready или появления v2 order команда до остановки проверяет Core FINANCIAL_PROTOCOL>=2 и все3 FINANCIAL_SCHEDULE>=2. Ручной откат ниже этих версий запрещён. Первая готовность включается только после успешного update-all и независимых проверок всех4 проектов. [Контракт](BOT_NATIVE.md).

Отдельный протокол чтения Supply: после owner-consent-v1-ready требуются
OWNER_POLICY_PROTOCOL>=1 и OWNER_POLICY_UPDATER_PROTOCOL>=1 в кандидате и
восстанавливаемых версиях. Ограниченный shadow-этап, проверка private snapshot,
совместимый резервный выпуск и активация описаны в [SUPPLY_OWNER_POLICY.md](SUPPLY_OWNER_POLICY.md).

## Core contract checks after readiness activation

Core candidate tests use the explicit `deploy/run_core_checks.py` entry point.
It redirects the owner-policy and optional next-meal reader defaults to absent
private temporary paths only inside that test subprocess, before discovery.
Explicit strict fixture paths remain effective. The production Store, Engine,
reader code, readiness files and environment policy are unchanged. Dynamically
loaded updater test fixtures also set their own absent gate paths.

A causal regression reuses an existing multi-owner weight test: a simulated
host marker makes the unisolated legacy fixture fail; the isolated runner passes
while the same explicit strict fixture still refuses the unknown owner. Optional
next-meal isolation and exception cleanup are covered too. Missing runner code
refuses the candidate test command. This keeps later updates usable after strict
activation without adding a production test bypass or weakening reader guards.
