# Явный план следующей еды

Core — единственное место хранения текущего выбора. Food предоставляет закрытый
по умолчанию инструмент «Что выбрать на следующий приём». Он читает до трёх
качественных идей из небольшого проверяемого каталога. Компоненты используют
канонический food_sources, все десять существующих групп исключения и выбор
рациона. Это не количественный рецепт, медицинская рекомендация или гарантия
отсутствия аллергенов; состав конкретного продукта проверяется отдельно.

Выбор не является съеденной едой. Никаких автоматических записей meals,
нутриентов, КБЖУ, полноты дня, meal anchors, целей, платежей, квот и AI attempts
он не создаёт. Фото и описание после еды используют прежний Food writer.
Нет ИИ, push, списка покупок или нового consumer. Данные Gym/Supply и предполагаемые
«дефициты» для этого инструмента не читаются.

## Владелец и доступ

Food `/api/next-meal` GET/POST проверяет существующую собственную native auth,
текущий paid/bundle/trial доступ Food и его настоящий trial limit. Аналитическая
суточная квота не тратится. Клиент не задаёт user_id. Затем Food отдельно от своей
SQLite транзакции вызывает `/internal/v1/connections/next-meal`: подписанный,
loopback-only control с source=food. Gym/Supply control и публичные assertions
не дают к нему доступ.

Core дополнительно проверяет Food membership, текущий source и global source
toggle, свежесть менее 120 секунд и paid либо действующий native trial в
профиле Food. Подписки Gym/Supply не требуются. Неизвестный/старый Core закрывает
этот инструмент, обычный Food продолжает работу. Явное открытие доступно во
время отдыха и hints-off; автоматических показов или напоминаний здесь нет.

## Один выбор и защита повторов

Food-день остаётся Europe/Moscow. `next_meal_choices` хранит одну строку на
Telegram subject: day, revision, idea_id либо отмену, preferences revision,
catalog version, время. `next_meal_receipts` — только owner/operation/hash/revision/
day/expiry, без копии рецепта. Логический срок 24 часа, до 64 активных receipts
на владельца, глобальная уборка не более 128 истёкших строк на успешную операцию.

POST содержит operation_id, action choose/cancel, day, choice_revision,
preferences_revision, catalog_version, data_reset_revision и при выборе idea_id.
Подмена payload под существующим operation_id отклоняется. Совпавший повтор
возвращает receipt вместе с текущим состоянием и никогда не восстанавливает
заменённый/отменённый/вчерашний выбор. Другой operation_id с прежней revision
отклоняется. Изменение выбора, проверка preferences и receipt находятся в одной
короткой BEGIN IMMEDIATE транзакции Core; ошибка receipt откатывает выбор.

Canonical restrictions по-прежнему только `connection_preferences` и её
существующий CAS writer. `connection_preference_versions` содержит лишь номер
версии, не второй набор preferences. Миграция сохраняет max(existing revision).
Триггеры повышают версию при update/delete/recreate, включая изменение без
повышения revision и возврат прежнего body. API preferences возвращает эту
монотонную revision. Старый клиент получает прежний 409 и должен перечитать
настройки. Удалённые настройки не становятся подтверждением отсутствия
ограничений: updated_at отсутствует, нужен явный save в «Связи и подсказки».
Неизвестные сохранённые ограничения закрывают подбор.

Браузер привязывает состояние и незавершённую операцию к серверному владельцу
и текущему proof. В sessionStorage хранится ограниченный receipt-intent с SHA256
proof, не сам proof. При отказе storage остаётся повтор в памяти. Смена proof,
аккаунта и закрытие раздела отменяют право позднего ответа менять экран.
После потери ответа используется тот же operation_id, включая восстановление
в той же вкладке/сессии. Другое устройство, новая proof и перенесённые черновики
не обещаются. Статус после действия сохраняет keyboard focus внутри раздела.

## Очистка данных Food

Существующий `Food db.purge_user` сохраняет paid account. Он теперь в одном
savepoint с прежней очисткой повышает `progressor_food_resets.revision` даже при
первом сбросе. Ошибка откатывает и историю, и epoch. Таблица содержит только
номер сброса владельца и остаётся вместе с retained account.

Food adapter экспортирует optional `data_reset_revision` в существующем базовом
профиле (старый экспорт = 0). Proxy передаёт текущую native revision и повторно
проверяет её после ответа. Пока private snapshot/poll Core не догнал сброс,
инструмент недоступен. Успешная сверка новой монотонной epoch очищает выбор и
receipts; старый экспорт не понижает `next_meal_owner_resets`. Запрос и receipt
до сброса не могут восстановить план. Это ограниченная задержка обычного
экспорта/опроса, без синхронного сетевого вызова в native purge.

Успешный полный Food snapshot с исчезнувшим membership также очищает новую
информацию выбора. Ошибка poll, отключение связи, отдых и окончание подписки
ничего не удаляют. Глобальные preferences других продуктов остаются. В Core
нет существующего публичного account-erasure endpoint: при явном удалении
identities cleanup trigger убирает новую metadata и preferences/version этого
subject; финансовые записи не затрагиваются.

## Отдельная активация и совместимый откат

По умолчанию серверный подбор выключен. Readiness-файл:
`/var/lib/progressor/next-meal-v1-ready`. Он отдельный от financial-v2 и
owner-consent-v1, не является согласием или платным grant.

Маркеры — literal top-level integer, читаются без выполнения candidate:

| Место | Маркер |
|---|---|
| Core progressor_core/next_meal.py | NEXT_MEAL_PROTOCOL = 1 |
| Core deploy/update_all.py | MEAL_CHOICE_UPDATER_PROTOCOL = 1 |
| Food db.py | FOOD_RESET_PROTOCOL = 1 |

Сначала обновить совместимый updater, подготовить совместимый Core/Food fallback,
проверить полный Linux набор и private резервную копию/восстановление. Затем
обычный update-all при отсутствии readiness-файла: инструмент ещё выключен.
После успешной завершённой транзакции подтвердить новые реально запущенные
Food bot/обе API и Core, свежую epoch-проекцию, совместимость установленного
updater/retained fallback. Только затем оператор под ОБЕИМИ существующими
блокировками updater создаёт root-owned readiness-файл. Агент разработки его
не создаёт. После активации нужна новая проверенная private backup.

При активном gate updater проверяет все три маркера перед prepare/switch,
продвижением updater и до любой операции rollback/interrupted recovery. Старый
Food purger запрещён: он иначе мог бы очистить журнал без повышения epoch.
Если fallback несовместим, сохраняются совместимый current, runtime/dropins и
updater, запускаются только проверенные retained службы; состояние требует
внимания вместо ложного «откат выполнен». Оба recovery guard взаимно проверяют
совместимость текущего Core при одновременно активных epoch. Базы не
восстанавливаются поверх новых записей.

Gate входит в существующий private gate collector: точные bytes, SHA256, mode
и present/absent manifest; реальный tar проверяет их при восстановлении. Обычный
кодовый откат gate не удаляет и не подменяет. Резервные копии ограничиваются
существующей проверкой свободного места/удержания update-all.

## Проверки и границы доказательств

SQLite/API тесты проверяют CAS, concurrent/replay, raw preferences ABA,
source/trial/rest/unknown, reset/clear-data и control audience. Браузерная
эмуляция использует настоящий Food markup/script с контролируемыми ответами:
потеря ответа/reload, смена владельца/proof, 409, закрытый раздел, отказ storage,
keyboard focus, 320/390 px и 100/200% текста в двух темах. Это не физическое
тестирование Telegram/iPhone и не доказательство улучшения конверсии.

Перед поставкой обязателен отдельный полный Linux прогон четырёх продуктов и
actual API/browser интеграция точного объединённого пакета. Тестовая копия D05
получила уже исправленный meal-day fixture `test_selected_privacy.py` из
следующего followup-пакета; продукт ради Windows файловых ограничений не менялся.
