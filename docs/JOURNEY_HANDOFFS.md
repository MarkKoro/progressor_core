# Точное действие и подтверждение проверки

Канонический UI и backend — только Progressor Core. Собственные формы, записи и правила доступа остаются в Gym/Food/Supply. Этот контракт описывает небольшой пакет D01–D03; он не является универсальным серверным движком всех идеальных маршрутов.

## Назначения

| Action | Собственная операция |
|---|---|
| food_goal | Food «Сегодня» → раскрытый «Профиль и напоминания», фокус; без расчёта/сохранения |
| food_log | Food текущий журнал блюд, фокус |
| open_food | Food недельный блок, фокус; не использовать для проверки цели |
| gym_plan | Личный Gym → настройки тренировочных дней через pendingView=plan; acting/onboarding guards сохраняются |
| supply_plan | Supply «Сегодня» → список собственных активных БАДов; дозы/отметки не меняются |
| supply_catalog | Только прежние разрешённые запросы железо/B12; обычный выбор и ввод владельца |

Native `ProgressorDomain` сообщает готовность, допустимость действия и ограниченный capture/restore своего экрана. Нельзя заменить собственную проверку доступа наличием navigation marker.

## Межпродуктовый переход

Общая кнопка использует прежний bootstrap/assertion bridge и фиксированные same-origin маршруты. `progressor_action`/`progressor_return=1` в URL — только метки; для обработки нужен соответствующий `sessionStorage` record. Произвольные URL, названия БАДов/дозы, профиль, даты, Telegram proof/assertions туда не передаются. Подписка `progressor_subscription=1` сохраняет прежний отдельный путь.

Один `progressor.transfer.v1` record на вкладку: version/from/to/action, разрешённый origin view, verified Core subject, SHA256 исходного proof, created/expires. Срок10мин — проектный выбор. До применения проверяются аккаунт/исходный proof/срок/назначение, готовность native и текущие собственные guard. Ожидание готовности ограничено10с. Ввод/нажатие пользователя во время ожидания отменяет автоматический переход; дальнейшее действие — явный повтор.

Возврат добровольный, к разрешённому собственному экрану. Не обещать перенос несохранённых drafts, точную позицию любого произвольного объекта, несколько вложенных intent или продолжение на другом устройстве. Изменённый draft/неподдерживаемый экран не покидаются ради такого handoff. Сбой storage/crypto/Core прекращает перенос с доступным объяснением; собственное приложение продолжает работу. В обычном состоянии верхняя навигация не получает новую постоянную строку; статус/возврат появляются только во время перехода или явной ошибки.

Эти метки не используются для автоматического возобновления покупки, применения Food цели, назначения дозы, отметки еды/приёма или завершения проверки. Обычные native push/deep links без tab-local record продолжают прежний вход; расширение их purpose-контракта — отдельная задача.

## Собственный кэш Gym

На receiving запуске SDK `initDataUnsafe.user` может отсутствовать. Локальные last values, workout drafts и pending AI apply принадлежат подтверждённому native `whoami` subject, сверяемому с исходным proof и Core subject, если Core session присутствует. Ключ различает verified viewer и acting native owner; `guest`/`self` без подтверждённого viewer больше не используются для чтения или записи. Legacy unbound записи нельзя приписывать первому следующему аккаунту.

Persistent ключ остаётся стабильным для того же verified owner при новом входе, а guard асинхронного ответа дополнительно меняется с proof/account/actor revision. Поздний ответ предыдущего аккаунта не восстанавливает его экран/черновик в новом. При смене verified viewer сбрасывается старое in-memory состояние без flush заметок и записей под новым proof. Недоступное storage или неподтверждённая identity прекращает только кэширование; native API и обычная запись продолжают собственные проверки. Core не становится обязательной зависимостью прямого native входа.

## «Проверил, всё подходит»

Только актуальные `change_weight`/`change_goal` hints получают `reviewable:true`. Поздняя обычная тренировка или отметка intake не доказывает пересмотра плана. Открытие/видимость/seen также не подтверждают его. Food weight-review может завершаться настоящей более поздней правкой цели.

Явная кнопка отправляет core-audience signed POST `/api/v1/me/hints/reviewed` с ровно `{target,delivery_key}`. Core проверяет включённый источник и получателя, собственный аккаунт, текущий source event/revision, fresh доступ, Supply consent, настройки и отдых. Старая/чужая/не-reviewable карточка не подтверждается.

Core хранит additive `hint_reviews(user_id,target,delivery_key,reviewed_at)`. `reviewed_at` — положительное конечное число Unix UTC seconds. Повтор применимого собственного подтверждения сохраняет исходное время. Receipt относится только к одному изменению и target; новая цель, другой target/аккаунт не закрываются им. Срок логического чтения/уборки90д. Native source DB, финансовые записи, workout/intake/дозы не изменяются.

UI проверяет200, `reviewed:true`, совпадение target/key и тип timestamp; блокирует двойную отправку. Поздний ответ не скрывает новую карточку/другой аккаунт и не перехватывает свежий ввод. Успех подтверждает ровно этот совет без немедленной рекламной замены. Ошибка позволяет безопасный явный повтор. Прежний общий dismissal7д остаётся другим действием.

## Проверка и дальнейшая работа

При изменении читать [JQ-v1](JOURNEY_QUALITY_RUBRIC.md). Девять критериев и G1–G7 зафиксированы до проектирования; null не заменяется нулём/успехом, прогноз концепции не является наблюдением пользователя. Не начислять пользу за повтор уже реализованной функции.

Проверки: `tests/test_hint_reviews.py`, native-hook/shell JS cases, Food helper/API/UI cases и общая actual HTML/API регрессия с временными данными. TestClient/браузерная эмуляция не подтверждают physical Telegram/iPhone, оплату или полную AA-сертификацию. Просмотр, переход, review и арифметика —0 платных AI-вызовов; дополнительных consumers/push нет.

Обновление — FF main4 и существующий update-all после проверенных резервных копий. Additive таблицы/триггеры сохраняются при откате кода; живые базы не восстанавливаются поверх последующих записей. Точные испытания и установленный результат фиксируются в WORK_LOG отдельно от этого описания контракта.
